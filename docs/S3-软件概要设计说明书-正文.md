系统开发语言：业务后端 Java（Spring Boot 3.x），AI 微服务 Python（FastAPI + LangChain）；数据库 MySQL 8.0。系统当前处于概要设计阶段，由本小组独立开发完成。

**2 项目设计概述**

**2.1 设计原则**

\(1\) **以用户为核心**：围绕大学生"学—练—复盘"的学习路径组织功能，界面简洁、操作符合移动端习惯，降低使用门槛。

\(2\) **业务与 AI 解耦、降级优先**：业务功能与 AI 功能分为两个后端独立部署，AI 微服务无状态、不连接数据库；AI 服务异常时核心学习功能必须可降级运行，这是一等设计约束。

\(3\) **分层与模块化**：业务后端采用 Controller-Service-DAO 三层架构，按功能模块（用户、词库、学习、复习、AI、统计、管理）划分包结构，模块间通过接口协作，保持高内聚低耦合。

\(4\) **契约先行**：前后端、业务后端与 AI 微服务之间先约定接口契约（统一响应结构、错误码、DTO），再并行开发。

\(5\) **安全与隐私**：密码哈希存储、JWT 鉴权、AI 密钥仅存于后端环境变量、日志不记录敏感信息。

\(6\) **可扩展与可持续**：词库可通过导入扩展，AI 模型可配置切换，数据库结构以 SQL 脚本版本化迁移。

**2.2 涉及范围**

（一）**功能模块**：用户模块（注册、登录、个人信息）、词库学习模块（词库浏览与选择、每日学习计划、学习打卡）、复习巩固模块（错题本、间隔复习）、AI 增强模块（AI 例句生成、AI 错题讲解、AI 学习报告）、数据统计模块（打卡热力图、掌握度曲线）、管理模块（词库与单词管理、用户管理、系统监控）。

（二）**技术架构**：前端覆盖微信小程序（原生框架）与网页管理端（React 18 + TypeScript + Vite + Ant Design）；业务后端 Spring Boot 3.x + MyBatis-Plus + MySQL 8.0；AI 微服务 FastAPI + LangChain + 大模型 API。

（三）**用户体验**：小程序端适配常见机型（rpx 单位）、AI 操作有加载态与超时提示、打卡与错题等时效数据进入页面即时刷新。

（四）**运营与维护范围**：管理员通过网页管理端维护词库数据与用户状态；系统日志分级记录 AI 调用与降级事件，便于运行监控。

**3 体系结构设计**

**3.1 体系结构设计总述**

系统总体采用前后端分离的分层体系结构，整体分四层：

1. **表示层**：微信小程序端（学生端）与网页管理端（React），负责页面展示与用户交互，统一通过 `services/` 网络层调用业务后端接口。
2. **业务逻辑层**：Spring Boot 业务后端，实现用户、词库、学习、打卡、错题、复习、统计与管理等全部业务逻辑，是唯一连接数据库的服务。
3. **AI 服务层**：FastAPI + LangChain AI 微服务，无状态部署，不连接数据库，所需数据由业务后端查询后传入，负责调用大模型 API 生成例句、讲解与报告。
4. **数据层**：MySQL 8.0 数据库，保存用户、词书、单词、学习记录与错题数据。

系统分层结构示意如下：

```
微信小程序端（学生）          网页管理端（管理员）
      │  REST（HTTPS）             │  REST（HTTPS）
      └────────────┬──────────────┘
                   ▼
        Spring Boot 业务后端（Controller-Service-DAO）
                   │                                │
        ┌──────────┴──────────┐                     │  HTTP
        ▼                     ▼                     ▼
   MySQL 8.0（唯一数据源）    统一缓存/降级策略   FastAPI + LangChain AI 微服务
                                                     │
                                                     ▼
                                                大模型 API（OpenAI 兼容）
```

**关键约束**：两个前端绝不直接请求 `ai-service/`，AI 内容一律经业务后端接口中转并支持降级；`ai-service/` 无任何数据库连接，永远不添加。

**3.2 总体架构概述**

（一）**业务后端（backend/）**：采用 Controller-Service-DAO 三层架构。

- Controller 层：接收请求、参数校验、调用 Service，不写业务规则；统一返回 `Result<T>` 包装结构。
- Service 层：承载业务规则（打卡连续天数计算、复习列表生成、AI 调用编排与降级），抛出自定义 `BizException`。
- DAO 层：基于 MyBatis-Plus 的 Mapper 接口与实体类，默认 `LambdaQueryWrapper` 动态查询，列表一律 `Page` 分页。

（二）**AI 微服务（ai-service/）**：FastAPI 应用，按功能提供 3 个接口（例句生成、错题讲解、学习报告），内部使用 LangChain 组织提示词模板与多步 Chain（学习报告为"拉取数据→分析→生成"多步编排）；无数据库连接、无状态，可独立水平扩展。

（三）**双前端**：小程序端（`miniprogram/`）按功能组织页面（index/study/review/mistakes/stats）；管理端（`frontend/`）按后端资源组织页面与类型（词库管理、用户管理、监控）。两端网络请求只发生在 `services/` 层，统一走 `utils/request`（baseURL、token 注入、`code !== "0"` 错误处理、401 跳转）。

**3.5 AI 微服务层设计（ai-service/）**

AI 微服务采用 FastAPI，目录结构如下：

```
ai-service/
├── app/
│   ├── main.py           # FastAPI 应用入口、路由注册
│   ├── core/             # 配置、日志统一配置、大模型客户端（OpenAI 兼容）
│   ├── chains/           # LangChain 编排：例句 Chain、讲解 Chain、报告 Chain
│   ├── schemas/          # 请求/响应模型（Pydantic）
│   └── routers/          # /ai/v1/example、/ai/v1/explain、/ai/v1/report
├── requirements.txt
└── .env.example          # API 密钥环境变量模板（不入库、不入仓）
```

设计要点：无状态服务，不连接任何数据库；大模型 API 密钥只从环境变量读取；失败抛 `HTTPException`，detail 使用稳定字符串；业务后端将一切 AI 侧失败映射为自有 `5xxx` 错误码，前端只面对一套错误词汇表。

**V1.4 实现补充——大模型供应商**：大模型供应商定为 **DeepSeek**（OpenAI 兼容 REST 接口），调用方式沿用 `langchain-openai` 的 `ChatOpenAI`，仅需替换 `base_url` 与 `model` 即可切换供应商；密钥经环境变量 `DEEPSEEK_API_KEY` 注入（`.env` 不入库）。选型理由：中文写作质量与英文释义生成满足例句/讲解场景、单价显著低于同级闭源模型、接口与 OpenAI 兼容因而**不锁定**供应商。超时与重试由调用方（业务后端）按 `§6` 契约的 15s/30s/60s 控制，ai-service 自身不设置长于该值的超时。

**3.6 数据层设计**

\(1\) 数据源：MySQL 8.0，InnoDB 引擎，全库 `utf8mb4`；仅 `backend/` 可连接数据库。

\(2\) 访问层：MyBatis-Plus；动态查询默认 `LambdaQueryWrapper`；列表接口一律 `Page` 分页；批量操作用 `saveBatch` / `removeByIds`；统计查询（热力图、掌握度曲线）在 SQL 中完成聚合。

\(3\) 迁移管理：数据库结构以纯 SQL 脚本管理，存放于 `backend/src/main/resources/db/`，每次变更新增有序脚本（`V001__init.sql`、`V002__xxx.sql`……），可直接导出作为课设交付物。

\(4\) 公共字段：每张表包含 `id`（BIGINT 自增主键）、`create_time`、`update_time`（DATETIME，MyBatis-Plus 自动填充）；面向用户数据（用户、学习记录、错题）使用逻辑删除（`deleted` 字段 + `@TableLogic`），物理删除仅限中间表记录。

**3.7 域模型设计**

系统核心域模型如下：

| **实体**       | **说明**                                   | **关键字段** |
|----------------|--------------------------------------------|--------------|
| User           | 用户（普通用户/管理员）                    | username、password_hash、role、status |
| WordBook       | 词书（四级/六级/考研）                     | name、category、word_count |
| Word           | 单词（属于某词书）                         | word、phonetic、translation、example |
| UserWordBook   | 用户 ↔ 词书 多对多中间表（已选词书）        | user_id、book_id |
| StudyRecord    | 学习记录（含每日打卡）                     | user_id、word_id、study_date、check_in_date、streak_days |
| MistakeEntry   | 错题记录                                   | user_id、word_id、wrong_count、mastered |

关系说明：一个用户可选多本词书，一本词书可被多个用户选择（`UserWordBook` 中间表）；一本词书含多个单词（`Word.book_id`）；用户对单词产生多条学习记录（`StudyRecord`）；错题（`MistakeEntry`）由学习/复习中答错的单词生成。

**4 接口设计**

**4.1 内部接口**

**4.1.1 设计原则**

（一）高内聚低耦合：接口按资源模块划分，一个接口只完成一个业务动作。

（二）统一响应：所有接口（无论成功失败）返回统一包装结构，错误通过 `code` 字段表达，而非仅靠 HTTP 状态码。

```json
{ "code": "0", "message": "ok", "data": { } }
```

- `code: "0"` 表示成功；其余均为失败，`message` 为可直接展示给用户的中文文案，失败时 `data` 为 `null`。
- 前端先判断 `code !== "0"`，不依赖 HTTP 状态码，不对包装结构做 try/catch。
- 业务错误 HTTP 状态保持 200；401/403 仅用于认证拦截器拒绝；500 仅用于真正未预期的崩溃。

（三）错误码分段管理（`common/ErrorCode.java`）：`1xxx` 认证/用户、`2xxx` 词库、`3xxx` 学习/打卡、`4xxx` 错题、`5xxx` AI 服务、`9xxx` 系统。

（四）稳定性：业务失败由 Service 抛 `BizException`，全局异常处理器统一转换为包装结构，Controller 绝不手工拼装错误响应体。

（五）可扩展：新增资源按同样模式扩展接口，DTO 与前端 `types/` 对齐（契约先行）。

**4.1.2 接口详情**

业务后端对外（两个前端调用）的主要 REST 接口如下。**路径规范（V1.2 起）：学生端/用户侧接口统一以 `/api/client/` 为前缀，管理端接口统一以 `/api/admin/` 为前缀**，认证与拦截据此分段。字段级请求/响应契约见《接口详细设计.md》（冻结版）。

| **模块** | **方法** | **路径**                     | **说明**                         |
|----------|----------|------------------------------|----------------------------------|
| 认证     | POST     | /api/client/auth/register    | 用户注册                         |
| 认证     | POST     | /api/client/auth/login       | 账号密码登录（返回 JWT；管理员同用此接口） |
| 认证     | POST     | /api/client/auth/wx-login    | 微信登录（小程序 code 换 openid，新用户自动注册） |
| 认证     | GET      | /api/client/auth/profile     | 获取个人信息                     |
| 认证     | PUT      | /api/client/auth/profile     | 修改个人信息                     |
| 词库     | GET      | /api/client/books            | 词库列表                         |
| 词库     | GET      | /api/client/books/{id}       | 词书详情（含单词分页）           |
| 词库     | POST     | /api/client/books/{id}/select    | 选择词书                     |
| 词库     | DELETE   | /api/client/books/{id}/select    | 移出词书（保留历史学习记录） |

**4.2 业务后端与 AI 微服务接口**

`backend/` 调用 `ai-service/` 的 HTTP 接口（均为 POST，JSON）：

| **接口**        | **路径**             | **输入（核心字段）**                 | **输出**               | **超时** |
|-----------------|----------------------|---------------------------------------|------------------------|----------|
| AI 例句生成     | /ai/v1/example       | word、translation、context            | example、mnemonic      | 15s      |
| AI 错题讲解     | /ai/v1/explain       | word、userAnswer、wrongContext        | explanation、advice    | 30s      |
| AI 学习报告     | /ai/v1/report        | studyStats（学习天数、打卡、错题等）   | report（分段文本）      | 60s      |

**降级约定**：AI 调用必须包裹超时与异常捕获。失败时返回降级结果（例句接口降级为词库内置例句 word.example 并标记 `degraded:true`；讲解与报告无兜底内容，返回 5xxx 错误码与"AI 暂时不可用"提示）并以 WARN 记录日志，绝不把大模型的原始错误透传给用户；学习/打卡流程不得依赖 AI 成功。

**4.3 外部接口**

（一）**大模型 API**：OpenAI 兼容的 `/v1/chat/completions` 接口，由 `ai-service` 调用。密钥只存在于 `ai-service` 环境变量中；错误信息绝不回显包含密钥的请求内容。

（二）**微信登录接口**：小程序端通过 `wx.login` 获取 code，业务后端调用微信 `code2Session` 换取 openid。openid 已存在则直接登录；不存在则自动创建用户（默认昵称与内置头像）并签发 JWT，响应标记 `isNewUser` 引导设置昵称。学生端以微信登录为主入口，账号密码登录保留给管理端与备用。

（三）**词库数据源（可选）**：开源词库数据文件（CSV/JSON），由管理员在管理端导入，导入接口在后端完成校验与批量写入。

**4.4 接口安全设计**

\(1\) 除注册、登录、微信登录外，所有业务接口要求携带 JWT（`Authorization: Bearer <token>`），由认证拦截器统一校验；401 时前端由 `utils/request` 统一清除 token 并跳转登录页。

\(2\) 管理端接口（`/api/admin/**`）额外校验用户角色为 ADMIN，未授权返回 403。

\(3\) AI 接口对普通用户开放但按用户鉴权；AI 密钥不出后端边界。

**5 功能模块设计**

**5.1 功能模块设计总述**

系统功能划分为六大模块：用户模块、词库学习模块、复习巩固模块、AI 增强模块、数据统计模块、管理模块。其中词库学习与复习巩固构成"学—练—复盘"核心闭环，AI 增强模块在其上提供个性化辅导，管理模块支撑数据维护与运营。

```
AI 单词学习打卡系统
├── 用户模块（注册、登录、个人信息）
├── 词库学习模块（词库浏览与选择、每日学习计划、学习打卡）
├── 复习巩固模块（错题本、间隔复习）
├── AI 增强模块（AI 例句生成、AI 错题讲解、AI 学习报告）
├── 数据统计模块（打卡热力图、掌握度曲线）
└── 管理模块（词库与单词管理、用户管理、系统监控）
```

**5.2 用户模块**

功能：用户注册、登录、个人信息查看与修改。

注册流程：小程序/管理端提交注册信息 → `AuthService` 校验用户名唯一性与密码格式 → BCrypt 加密存储 → 创建用户记录（默认角色 USER）→ 返回注册结果。

登录流程：用户输入账号密码 → `AuthService` 校验密码 → 签发 JWT（含 userId、role、过期时间）→ 返回 token 与用户信息；登录失败记录 WARN 日志（不记录密码）。

关键类：`AuthController`、`AuthService`、`UserService`、`UserMapper`。

**5.3 词库学习模块**

功能：词库浏览与选择、每日学习计划、学习打卡。

（一）词库浏览与选择：用户查看词库列表（内置四级/六级/考研词库），选择词书后写入 `UserWordBook` 中间表；同一用户可同时选择多本词书。

（二）每日学习计划：`StudyService` 按用户已选词书生成当日学习计划（默认每词书每日 20 个新词，按词书内未学单词顺序与复习优先级排序），返回待学单词列表。

（三）学习打卡：用户完成当日学习后点击打卡 → 逐词写入 `StudyRecord`（标记已学）→ 更新 `check_in_date` 与连续打卡天数 `streak_days`（若与上次打卡日连续则 +1，否则重置为 1）→ 返回打卡结果。同一日期重复打卡幂等处理（"今日已打卡"错误码 3xxx）。

关键类：`StudyController`、`StudyService`、`WordBookService`、`WordMapper`、`StudyRecordMapper`、`UserWordBookMapper`。

**5.4 复习巩固模块**

功能：错题本、间隔复习。

（一）错题本：学习/复习中答错的单词自动收录进 `MistakeEntry`（含来源、错误次数）；用户可查看错题列表（分页）、请求 AI 讲解、标记"已掌握"（`mastered=true`）或手动移除。列表查询用 `selectBatchIds`/联查避免 N+1。

（二）间隔复习：`ReviewService` 按简化间隔复习算法（基于最近学习时间与错题次数计算复习间隔：1 天→3 天→7 天→15 天）生成今日待复习列表；用户完成复习后更新记录并回写错题状态。复习列表为计算生成，不设独立存储表。

关键类：`MistakeController`、`MistakeService`、`ReviewController`、`ReviewService`、`MistakeEntryMapper`。

**5.5 AI 增强模块**

功能：AI 例句生成、AI 错题讲解、AI 学习报告。三者为可独立降级的增强功能。

（一）AI 例句生成：用户点击单词"AI 例句" → 前端调用 `/api/client/ai/example` → `AiService` 携带单词与上下文请求 `ai-service` → LangChain 例句 Chain 组装提示词调用大模型 → 返回例句与助记；失败时返回缓存例句或"AI 暂时不可用"降级提示。

（二）AI 错题讲解：用户选择错题 → 后端携带错题单词、用户答案与上下文请求讲解接口 → 返回讲解与建议；讲解后用户可标记"已掌握"。

（三）AI 学习报告：用户请求生成报告 → `StatsService` 汇总学习数据（学习天数、打卡、错题分布等）→ `ai-service` 学习报告 Chain 多步编排（分析→生成）→ 返回图文报告；数据不足时返回提示，不调用 AI。

**降级设计（一等约束）**：AI 调用全部带超时与异常捕获；降级时以 WARN 记录日志（功能名、耗时、降级结果），供监控观测；核心学习、打卡、复习流程不依赖 AI 成功。

关键类：`AiController`、`AiService`、`StatsService`、`ai-service` 的 `routers/` 与 `chains/`。

**5.6 数据统计模块**

功能：打卡热力图、掌握度曲线。

（一）打卡热力图：`StatsService` 按月聚合 `StudyRecord.check_in_date` 生成热力图数据（SQL 聚合，不加载原始记录到内存）。

（二）掌握度曲线：按日期聚合每日学习/复习单词量与错题量，结合错题掌握状态计算掌握度，返回曲线数据点序列。

关键类：`StatsController`、`StatsService`、`StudyRecordMapper`。

**5.7 管理模块**

功能：词库与单词管理、用户管理、系统监控。

（一）词库与单词管理：管理员批量导入词库（CSV/JSON 校验后 `saveBatch` 写入）、单词增删改查（分页）。

（二）用户管理：用户列表（分页）、禁用/启用（改变 `status`，禁用后 JWT 校验失效）；操作记 INFO 日志并带操作者 id。

（三）系统监控：`GET /api/admin/monitor/ai-stats` 展示 AI 调用成功/降级统计（一期用进程内内存计数器 `AiMetrics`，重启清零；每次降级另有 WARN 日志）、降级事件明细与注册用户数。

关键类：`AdminController`、`WordBookService`、`UserService`、`WordMapper`。

**7 数据库设计**

**7.1 数据库设计总述**

数据库采用 MySQL 8.0，InnoDB 引擎，全库 `utf8mb4`。核心表共 **7** 张：用户表、词书表、单词表、用户-词书中间表、学习记录表、错题表、**用户单词学习进度表（word_progress）**。所有表包含公共字段 `id`（BIGINT 自增主键）、`create_time`、`update_time`；用户、学习记录、错题、单词使用逻辑删除（`deleted`），中间表记录物理删除。外键仅在应用层维护，不加数据库级外键约束，但所有关联列建索引。

**V1.3 实现补充**：`create_time`/`update_time` 为裸 `DATETIME NOT NULL`，**不设数据库默认值**，统一由业务后端 ORM 层（MyBatis-Plus `MetaObjectHandler`）单套机制填充——避免「数据库默认值 + ORM 填充」两套时间来源不一致。`study_record` 加唯一索引 `uk_study_record_user_word_date_type`（用户+单词+日期+类型），`user_word_book` 加唯一索引 `uk_user_word_book_user_book`（用户+词书），以数据库约束兜底并发重复写入（不依赖「先查后插」）。
