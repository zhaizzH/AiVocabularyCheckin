# 思考指南

> **目的**：扩展思考维度，捕捉那些"没想到"的问题。

---

## 为什么需要思考指南？

**大多数 Bug 和技术债来自"没想到"，而不是能力不足**：

- 没想到层与层之间会发生什么 → 跨层 Bug
- 没想到代码模式在重复 → 重复代码到处都是
- 没想到边界情况 → 运行时错误
- 没想到未来的维护者 → 代码读不懂

这些指南帮助你在**写代码之前问对问题**。

## 快速参考：思考触发器

### 什么时候要思考跨层问题

- [ ] 功能涉及 3 层以上（API、Service、组件、数据库）
- [ ] 数据格式在层之间发生变化
- [ ] 多个消费方需要同一份数据
- [ ] 不确定某段逻辑该放哪一层
- [ ] 正在新增事件类型、JSONL 记录、RPC 负载或配置字段
- [ ] UI / 命令代码开始直接对原始负载字段做类型断言

→ 阅读[跨层思考指南](./cross-layer-thinking-guide.md)

### 什么时候要思考代码复用

- [ ] 正在写的代码与已有代码相似
- [ ] 同一模式出现了 3 次以上
- [ ] 要在多处添加同一个字段
- [ ] **正在修改任何常量或配置**
- [ ] **正在新建工具/辅助函数** ← 先搜索！
- [ ] 两个文件各自对同一个无类型负载字段做局部断言
- [ ] 多个分支各自根据 `kind` / `action` 更新同一份派生状态

→ 阅读[代码复用思考指南](./code-reuse-thinking-guide.md)

### 验证 AI 交叉评审结果时

- [ ] 评审称"用户输入可能是恶意的" → 核实真实数据来源（内部清单？用户配置？外部 API？）
- [ ] 评审标记"缺少校验" → 数据是否来自可信的内部来源？
- [ ] 评审说"行为变更" → 读代码注释——是否为有意设计？
- [ ] 评审在测试中发现"Bug" → 在心里删掉被测功能——测试还过吗？还过 → 同义反复式测试

**AI 评审常见误报模式**：
1. **信任边界混淆**：把内部数据（内置 JSON 清单）当作不可信的外部输入
2. **无视设计注释**：把代码注释中说明的有意行为当作 Bug
3. **变量误读**：没有追到变量的真实定义（例如按路径而非名称建键的 Map）

**验证规则**：每条 CRITICAL/WARNING 结论都必须对照真实代码核实后再排优先级。AI 评审预留约 35% 的误报率。

## 修改前规则（关键）

> **修改任何值之前，务必先搜索！**

```bash
# 搜索你即将修改的值
grep -r "value_to_change" .
```

这一个习惯能避免大多数"忘了改 X"类 Bug。
