# 跨层思考指南

> **目的**：动手实现之前，先想清楚跨层数据流。

---

## 问题所在

**大多数 Bug 发生在层与层的边界上**，而不是层内部。

常见的跨层 Bug：

- API 返回格式 A，前端期望格式 B
- 数据库存的是 X，Service 转成 Y，过程中丢了数据
- 多个层各自实现了同一逻辑，实现还不一样

---

## 实现跨层功能之前

### 第 1 步：画出数据流

把数据的流动画出来：

```
来源 → 转换 → 存储 → 读取 → 转换 → 展示
```

对每一个箭头，问自己：

- 这里的数据是什么格式？
- 可能出什么错？
- 谁来负责校验？

### 第 2 步：识别边界

| 边界 | 常见问题 |
|------|----------|
| API ↔ Service | 类型不匹配、字段缺失 |
| Service ↔ 数据库 | 格式转换、null 处理 |
| 后端 ↔ 前端 | 序列化、日期格式 |
| 组件 ↔ 组件 | props 结构变化 |

### 第 3 步：定义契约

对每个边界明确：

- 确切的输入格式是什么？
- 确切的输出格式是什么？
- 可能出现哪些错误？

---

## 常见跨层错误

### 错误 1：隐式的格式假设

**反面**：不看就假设日期格式

**正面**：在边界处做显式的格式转换

### 错误 2：校验分散

**反面**：同一件事在多个层各校验一遍

**正面**：只在入口校验一次

### 错误 3：抽象泄漏

**反面**：组件知道数据库表结构

**正面**：每层只了解自己的邻居

### 错误 4：每个消费方各自解析同一负载

**反面**：命令读取 JSONL 事件并内联做字段断言：

```typescript
const thread = (ev as { thread?: string }).thread;
const labels = (ev as { labels?: string[] }).labels;
```

看起来很局部，但实际上每个消费方都私有地拥有一份事件契约。下次改
字段时，改了一个命令、漏了另一个。

**正面**：在事件边界解码一次，然后导出类型化的投影：

```typescript
if (!isThreadEvent(ev)) return false;
return ev.thread === filter.thread;
```

**规则**：对于追加式日志、JSON 流、RPC 负载或配置文件，只设一个
拥有者负责：

- 事件 / 负载类型定义
- 从 `unknown` 出发的类型守卫与归一化
- UI 命令使用的元数据投影
- 从事实来源重放状态的 reducer

渲染代码可以做字段格式化，但绝不能重新定义负载契约。

## 跨层功能检查清单

实现之前：

- [ ] 画出了完整的数据流
- [ ] 识别了所有层边界
- [ ] 定义了每个边界的格式
- [ ] 决定了校验发生在哪一层

实现之后：

- [ ] 用边界值（null、空、非法）测过
- [ ] 验证了每个边界的错误处理
- [ ] 检查了数据往返（round-trip）后不丢失
- [ ] 检查了消费方 import 的是共享解码器 / 投影，而不是局部断言
- [ ] 检查了派生状态指向来源事件标识（`seq`、`id`、`version`），
      而不是自造第二套游标

---

## 什么时候需要画流程文档

以下情况值得写详细的流程文档：

- 功能横跨 3 层以上
- 多人协作
- 数据格式复杂
- 该功能以前出过 Bug

---

## 事件日志 / 投影边界

追加式日志本身就是跨层契约。一个事件的旅程：

```
输入 → 事件写入器 → events.jsonl → 读取器 → 过滤器 → reducer → 展示
```

### 新增事件类型或字段后的检查清单

- [ ] 事件类型已加入中央事件分类
- [ ] 事件层有类型化的事件变体或类型守卫
- [ ] 来自用户输入或 JSON 的数组/对象字段有归一化辅助函数
- [ ] `seq` / `id` 只在事件写入器中赋值
- [ ] 过滤器与 reducer 消费类型守卫，不做局部断言
- [ ] 展示代码消费 reducer 输出或类型化事件，不碰原始 JSON
- [ ] 至少一个回归测试证明历史重放与实时过滤使用同一套过滤模型

## 本项目中的跨层边界

本项目有 5 个明确的跨层边界，改动前先对照：

1. **`miniprogram/` ↔ `backend/`**：HTTP + `Result<T>` 包装。契约先行——
   接口变更先改契约文档，两端再并行开发。
2. **`frontend/` ↔ `backend/`**：同上；`frontend/src/types/` 与后端 DTO
   一一对应，后端 DTO 改名必须同步。
3. **`backend/` ↔ `ai-service/`**：内部 HTTP。AI 服务无状态，所有数据由
   业务后端传入；任何 AI 失败由业务后端映射为 `5xxx` 错误码 + 降级，
   前端永远看不到 AI 服务的原始错误。
4. **`ai-service/` ↔ 大模型 API**：外部依赖，必须超时 + 降级；密钥只在
   环境变量中。
5. **`backend/` ↔ MySQL**：MyBatis-Plus 实体映射；手写 XML 不会自动带
   `deleted = 0` 逻辑删除条件，边界处手动补。
