# 错误处理

> 本项目的错误处理方式。

---

## 概览

- 业务后端所有接口返回统一的包装结构；错误通过 `code` 字段表达，
  而不是仅靠 HTTP 状态码。
- 业务失败统一抛出一个自定义异常类型，由全局异常处理器转换为包装结构——
  Controller 绝不手工拼装错误响应体。
- **AI 降级是一等错误路径**（需求规格说明书要求）：当 AI 微服务或大模型
  API 故障时，核心学习功能必须继续可用，用户看到明确的降级提示。

---

## 错误类型

- `backend/`：定义一个 `BizException(String code, String message)`
  （放在 `common/` 或 `exception/`）。错误码常量在 `common/ErrorCode.java`
  中按模块分段：`1xxx` 认证/用户、`2xxx` 词库、`3xxx` 学习/打卡、
  `4xxx` 错题、`5xxx` AI 服务、`9xxx` 系统。
- 不搞按模块划分的异常继承体系——本规模下一个"错误码 + 消息"足够。
- `ai-service/`：抛 `HTTPException`，detail 使用稳定的字符串；业务后端把
  一切 AI 侧失败映射为自己的 `5xxx` 错误码，因此前端只需面对一套错误词汇表。

---

## 错误处理模式

- 可预期的业务失败（"未选择词库"、"今日已打卡"）由 Service 抛
  `BizException`。未捕获的异常由全局处理器兜底为通用 `9xxx` 系统错误。
- 一个 `@RestControllerAdvice` 统一处理：`BizException` → 对应错误码；
  参数校验失败（`@Valid` / `MethodArgumentNotValidException`）→
  `400` 段错误码 + 第一个字段的提示信息；其余异常 → 记录日志 +
  通用系统错误。
- AI 调用（`backend` → `ai-service` → 大模型 API）必须包裹超时与异常捕获。
  失败时：返回降级结果（缓存的例句 / "AI 暂时不可用"提示），并以 WARN
  记录日志——绝不把大模型的原始 500 透传给用户。
- 大模型 API 密钥只存在于环境变量中；错误信息绝不回显包含密钥的请求内容。

---

## 接口错误响应

所有响应（无论成功失败）统一为以下结构：

```json
{
  "code": "0",
  "message": "ok",
  "data": { }
}
```

- `code: "0"` 表示成功。其余均为失败；`message` 为可直接展示给用户的
  中文文案；失败时 `data` 为 `null`。
- 前端/小程序代码先判断 `code !== "0"`——不要依赖 HTTP 状态码，
  也不要对包装结构做 try/catch。
- 业务错误 HTTP 状态保持 `200`；`401`/`403` 仅用于认证拦截器拒绝，
  `500` 仅用于真正未预期的崩溃。

---

## 常见错误

- 捕获异常后返回 `Result.ok(null)`——这会把失败对客户端和日志同时隐藏。
  要么转换为有意义的错误码，要么交给全局处理器。
- 让 AI 超时阻塞学习类接口。学习/打卡流程不得依赖 AI 成功；
  AI 内容独立获取、独立降级。
- 把任意异常的 `e.getMessage()` 直接返回给客户端——内部消息会泄露
  SQL 与堆栈细节；应映射为 `ErrorCode` 中的文案。
